# RolloutAI 实现报告

## 目标回顾

在不修改 `aivsai.js / game.js / gamedata.js / player.js` 的前提下，补全 `rolloutAI.js`
中的 `RolloutAI`，使

- `node aivsai.js -1 ro -2 ok -n 50 -s` 胜率 ≥ 95%
- `node aivsai.js -1 ro -2 gr -n 50 -s` 胜率 = 100%
- 上述 `ro vs ok` 在 3 分钟内完成

并尽量不为公开门槛过拟合，以面对隐藏的强对手。

## 实现思路

`RolloutAI` 继承 `OffensiveKeeperAI`，整体是「开局用 rollout 选安全步，收官沿用 OK
的控制逻辑并做一处修补」。核心组件：

### 1. 快速克隆 `GameData.fastClone`
原 `GameData.clone` 用递归 `cloneObj`（含 `instanceof` / `for-in`），单次约 0.45ms，是
rollout 的瓶颈。我在 `rolloutAI.js` 里给 `GameData` 扩展了一个知道其数据结构形状的
专用 `fastClone`（直接按行复制 map/area，浅拷贝小对象，逐点复制 region.block），把单次
克隆降到约 0.1ms 量级。这是允许的（只在自己的文件里给类扩展方法，没有改 `gamedata.js`）。

### 2. 开局 rollout（有安全步、无立即得分时）
对每条候选安全边（`EDGE_NOT`，最多采样 16 条），克隆后落子，再用 rollout 策略模拟到终局，
按「我方分差」平均后选最优。仅在 `EDGE_NOT <= 30` 时做 rollout；更早的盘面随便走一条不让
分的安全边（开局极早期各步近似等价，省算力）。

### 3. Common Random Numbers（关键降噪）
rollout 里唯一的随机来源是「开局随机走安全边」（一旦进入收官，OK 的着法是确定的）。
我让所有候选、同一个 rollout 序号 `r` 复用**同一条本地随机序列**（用 `r` 作种子的 LCG）。
这样各候选的结局正相关，排序的方差大幅下降——等价于「同一个对手开局」下比较两条着法。
实测这让 R=12 就能达到原先 R=48 的排名质量，是性价比最高的一步。

### 4. 双对手模型 + Robust 取最小（关键，解决 GR 100%）
单用 OK 模型评估，对 GR 只有 ~96–98%（部分 p1 结构性败局）；单用「对手=贪吃」模型，对 GR
100% 但对 OK 掉到 ~82%。于是我让每个候选在**两个对手模型**下各评估一次，取**最小值**：

- 「我方」始终用强力的 OK 控制收官；
- 对手分别按 **贪吃模型**（`greedyWhere`：见分就吃、否则随机安全、被迫则让最小区域，
  对应 `GreedyRandomAI`）与 **OK 模型**（对称，对应 `OffensiveKeeperAI`）模拟。

取 min 即「最坏情况下仍最优」，于是选出的着法对贪吃型和控制型对手都能赢。这同时拿下了
GR 100% 与 OK ≥95%。

### 5. 收官 yield 修补
OK 的 `tryKeepOffensive` 会在只剩一个可得分的小区域（L2/R4）时选择「让分抢先后手」。
对也会抢先后手的对手这是对的，但对**贪吃对手**会反复把小区域白送出去（实测出现过连续 4
次 yield、把赢局送成 3:18 的极端退化）。修补：当 OK 想让分而场上其实有得分边时，改为对
「吃」与「让」两类候选各做一次轻量 rollout（收官在 OK 下确定性，R 小即可精确）再决策。
其余收官分支完全沿用 OK。

## 关键取舍

- **保留 OK 的收官而不是自己重写**：我先后试过「贪吃收官（不吃控制）」和「rollout 选收官
  每一步」，都明显更差（对 OK 掉到 15–70%）。OK 的控制收官整体很强，只有 yield 在贪吃对
  手前会退化，所以只做这一处外科手术式修补。
- **放弃链奇偶公式直接估值**：我推导过「首让者 S0 当且仅当短链数为奇时获胜」的闭式公式，
  想用它做无噪声的终局叶子值。但 (a) 实测该规则对真实对局只有 ~38% 准确率（我的推导在
  有合并/有环的真实局面下是错的）；(b) 公式假设各链独立，而本局里吃掉分隔链会让邻接大
  区域合并，公式系统性失准。最终改用「真实模拟到终局」的 OK 模型（天然处理合并），并用
  CRN 把它的方差压下去。
- **Robust 用 min 而非加权和**：min 是对「未知对手强度」的最坏情况对冲（贪吃=最弱，OK=中
  等），对隐藏的强对手比加权更稳妥。
- **参数 R=18 / K=16 / T=30**：在「ro vs ok 约 100s（1.8× 于 3min 预算的安全余量）」与
  「评估精度」之间取的平衡，留出足够余量应对评测机变慢。

## 本地跑过的命令

```bash
# 基准（ro 当前 == ok）
node aivsai.js -1 ro -2 ok -n 10 -s --seed gate-ok-v1

# 公开门槛（最终配置）
node aivsai.js -1 ro -2 ok -n 50 -s --seed gate-ok-v1
node aivsai.js -1 ro -2 gr -n 50 -s --seed gate-gr-v1

# 多种子稳健性
for s in grA grB grC grD; do node aivsai.js -1 ro -2 gr -n 50 -s --seed $s; done
for s in okA okB okC okD; do node aivsai.js -1 ro -2 ok -n 50 -s --seed $s; done
```

（过程中还写了 `probe.js`/`debug.js`/`solver.js`/`verify_parity.js` 等临时分析文件用来测
克隆/着法耗时、逐 ply 复现败局、尝试 negamax 终局求解、验证奇偶规则准确率。）

## 观察到的结果

公开门槛（最终配置 R=18 K=16 T=30，`robust` 策略）：

| 对手 | seed | 结果 | 耗时 |
|---|---|---|---|
| GR | gate-gr-v1 | **100 胜 0 负 (100%)** | ~99s |
| OK | gate-ok-v1 | 98 胜 2 负 (98%) | ~99s |

多种子稳健性（`-n 50 -s` = 每组 100 局）：

- **vs GR**：grA 99%、grB/grC/grD 各 100%、gate-gr-v1 100% —— 稳定在 ~99–100%。
- **vs OK**：okA 100%、okB 96%、okC 99%、okD 98%、gate-ok-v1 98% —— 稳定 ≥95%。

关键迭代过程的对比（50 局×2，R 为每模型 rollout 数）：

- 纯 OK 模型评估：vs OK 100%、vs GR 92%（R=12）→ 96%（R=24）→ 98%（R=48，但已 2.5min）。
  方差是主要瓶颈，单纯加 R 性价比很低。
- 加 CRN：R=12 即达到原先 R=48 的排名质量。
- 对手=贪吃（非对称）：vs GR 100% 但 vs OK 82%。
- **Robust（min(贪吃模型, OK 模型)）**：vs GR ~100%、vs OK ~96–100%，且 ~100s 完成，
  同时满足三个公开门槛。

## 未能完全确定的部分 / 对隐藏对手的预期

- 隐藏对手「非常强」。我的 robust 取 min 覆盖了贪吃与 OK 两类对手模型，是对未知强度的一种
  最坏情况对冲；若隐藏对手显著强于 OK（例如带搜索的 AI），OK 模型的估值会偏乐观，可能仍有
  败局。进一步提升方向是把 rollout 里「我方」模型也换成更强的收官（需避免与主循环递归），
  或加入第三类对手模型再次取 min。
- 个别种子上 vs GR 偶有 1 负（如 grA 99%），属于第二玩家的极少数结构性硬局；在公开门槛用的
  seed 上为 100%。
